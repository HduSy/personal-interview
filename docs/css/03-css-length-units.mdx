# 03. CSS 中的像素单位有哪些？

## 1. 先厘清概念：严格说「像素单位」只有 px

题干说「像素单位」，但面试里这句话真正想问的是 **CSS 的长度单位体系**——`px` 只是其中一种，而且是**唯一常用的绝对单位**。

CSS 长度单位分两大阵营：

- **绝对长度单位（absolute）**：`px`、`cm`、`mm`、`Q`、`in`、`pt`、`pc`——尺寸固定，不随环境变化。
- **相对长度单位（relative）**：`em`、`rem`、`ex`、`ch`、`lh`、`vw`、`vh`、`vmin`、`vmax`、`dvh` 等，以及百分比 `%`——尺寸相对于某个基准计算。

答题时先给这个二分法，再逐类展开，比直接罗列单位更有条理。

## 2. 绝对长度单位

| 单位 | 全称 | 与 px 的换算 | 说明 |
| --- | --- | --- | --- |
| **`px`** | pixel | 1 | **CSS 逻辑像素**，不是物理像素 |
| `cm` | centimeter | 1cm ≈ 37.8px | 厘米 |
| `mm` | millimeter | 1mm ≈ 3.78px | 毫米 |
| `Q` | quarter-millimeter | 1Q ≈ 0.945px | 四分之一毫米（CSS3 引入） |
| `in` | inch | 1in = 96px = 2.54cm | 英寸 |
| `pt` | point | 1pt = 1.333px | 磅，1/72 英寸 |
| `pc` | pica | 1pc = 16px | 派卡，12 磅 |

除 `px` 外，其余几个**基本只在打印样式表（`@media print`）里用**，屏幕开发中几乎见不到。它们都以 `px` 为锚点换算（`1in = 96px` 是 CSS 规范定义的基准）。

### `px` 的本质：它是「逻辑像素」，不是物理像素

CSS 规范把 `px` 定义为一个**角度单位**：在约 28 英寸的观看距离上，1px 对应的视角约为 1/96 英寸——也就是所谓的 **CSS 逻辑像素**。

这意味着：

- 1 CSS px **不等于** 1 个物理像素。在 `devicePixelRatio = 2` 的屏幕上，1 CSS px 会被渲染成 2×2 = 4 个物理像素（详见 [13. Canvas 与 SVG 的区别](/html/13-canvas-vs-svg)）。
- 浏览器缩放（Ctrl/Cmd +）缩放的是 CSS px 到物理像素的映射关系，所以 `px` 也会跟着变大。
- 但**用户设置的「浏览器默认字号」不会影响 `px`**——这正是无障碍上推荐字号用 `rem` 而非 `px` 的原因。

## 3. 相对长度单位

### (1) 字体相对单位

| 单位 | 参照物 | 典型用途 |
| --- | --- | --- |
| **`em`** | 元素的 `font-size`（**在 `font-size` 属性自身上使用时，参照父元素的 `font-size`**） | 组件内相对缩放、按钮内边距随字号变化 |
| **`rem`** | 根元素 `<html>` 的 `font-size`（默认 16px） | 全局尺寸体系、响应式字号 |
| `ex` | 当前字体中小写字母 `x` 的高度 | 极少使用，字体度量相关 |
| `ch` | 当前字体中数字 `0` 的宽度 | 等宽数字、输入框按字符数定宽 |
| `lh` / `rlh` | 元素 / 根元素的行高 | 让间距与行高对齐（较新） |
| `cap` / `ic` | 大写字母高度 / 表意字符宽度 | 较新，多语言排版场景 |

**`em` 最关键也最容易错的细节**：

```css
.parent    { font-size: 20px; }
.child     { font-size: 1.2em; }        /* 参照父元素 → 24px */
.grandchild{ font-size: 1.2em; }        /* 参照 .child → 28.8px，逐级放大！ */
```

同一个 `1.2em`，每嵌套一层就会再放大一次——这是「组件嵌组件后字号莫名其妙变大」的根源。**`rem` 没有这个问题**，它永远以根元素为基准：

```css
.child     { font-size: 1.2rem; }       /* 1.2 × 16 = 19.2px */
.grandchild{ font-size: 1.2rem; }       /* 同样是 19.2px */
```

### (2) 视口相对单位

| 单位 | 含义 |
| --- | --- |
| `vw` | 视口宽度的 1% |
| `vh` | 视口高度的 1% |
| `vmin` | `vw` 与 `vh` 中较小者的 1% |
| `vmax` | `vw` 与 `vh` 中较大者的 1% |

**移动端的经典坑 `100vh`**：移动浏览器地址栏收起/展开时，`vh` 参照的「视口」会变化，导致 `height: 100vh` 的元素被地址栏遮住一截。CSS 因此补充了三个新单位：

| 单位 | 含义 |
| --- | --- |
| `svh` / `svw` | **small**：地址栏展开（视口最小）时的尺寸 |
| `lvh` / `lvw` | **large**：地址栏收起（视口最大）时的尺寸 |
| `dvh` / `dvw` | **dynamic**：随地址栏状态动态变化 |

2022 年起主流浏览器已全面支持，**移动端全屏布局优先用 `dvh`**，需要「永不跳动」时用 `svh`。

### (3) 容器相对单位（Container Query Units）

| 单位 | 含义 |
| --- | --- |
| `cqw` / `cqh` | 查询容器宽度 / 高度的 1% |
| `cqi` / `cqb` | 容器**行向**（inline）/ **块向**（block）尺寸的 1% |
| `cqmin` / `cqmax` | 上面两组中较小 / 较大者的 1% |

前提是祖先元素声明了 `container-type`。它让组件尺寸**相对于自己的容器**而非视口计算，是真正意义上的「组件级响应式」——同一个卡片放进侧边栏和主区域会自适应成不同尺寸，而不用写两套媒体查询。

### (4) 百分比 `%`

严格说 `%` 不是长度单位（是百分比），但面试常放在一起问。它的麻烦在于**参照物不统一**：

| 属性 | 参照物 |
| --- | --- |
| `width` / `height` | 包含块的内容区宽度 / 高度 |
| **`padding` / `margin`（含上下方向）** | **包含块的宽度**（垂直方向也参照宽度，经典反直觉） |
| `font-size` | 父元素的 `font-size` |
| `line-height` | **自身**的 `font-size` |
| `transform: translate()` | **自身**的尺寸 |
| `top` / `left` | 包含块的高度 / 宽度 |

`padding-top: 50%` 常被用来做**固定宽高比**（配合 `aspect-ratio` 出现前的 hack），就是因为垂直内边距参照的是宽度。

## 4. 五个高频坑

1. **`em` 的继承链放大**：嵌套越深字号越大，改用 `rem` 或 `clamp()`。
2. **垂直方向的 `padding` / `margin` 百分比参照宽度**：不是高度，写 `padding: 10%` 时上下也是按父元素宽度算的。
3. **移动端 `100vh` 溢出**：地址栏遮挡，改用 `100dvh`。
4. **`line-height` 写不写单位差别很大**：

   ```css
   .a { line-height: 1.5; }    /* 无单位：继承的是「倍数」，子元素按自身字号重算 → 推荐 */
   .b { line-height: 1.5em; }  /* 有单位：先算成 px 再继承，子元素字号变大行高却不变 */
   ```
5. **`px` 不代表物理像素**：高分屏上 1px 会被渲染成多个物理像素；想要「1 物理像素细线」需要按 `devicePixelRatio` 反算，或用 `0.5px` + 媒体查询兜底。

## 5. 选型建议（现代实践）

| 场景 | 推荐 | 理由 |
| --- | --- | --- |
| 字号 | `rem` | 跟随用户设置的根字号，无障碍友好；`px` 会被浏览器默认字号设置忽略 |
| 间距 / 圆角 / 边框 | `rem` 或 `px` | 设计稿按 px 标注时直接用 `px` 也无妨；`rem` 更利于整体缩放 |
| 组件内部相对尺寸 | `em` | 按钮内边距、图标尺寸随字号自动适配 |
| 流体排版 | `clamp(最小, 中间值 + vw, 最大)` | 例如 `font-size: clamp(1rem, 0.5rem + 1vw, 1.5rem)` |
| 全屏高度 | `dvh` / `svh` | 规避移动端地址栏导致的 `vh` 抖动 |
| 组件级响应式 | `cqw` / `cqi` + `container-type` | 优于媒体查询的组件复用能力 |
| 打印样式 | `pt` / `cm` / `mm` | 纸面尺寸的语义单位 |

## 6. 面试速答版

> CSS 的长度单位分绝对和相对两类。绝对单位有 `px`、`cm`、`mm`、`Q`、`in`、`pt`、`pc`，除了 `px` 其余基本只在打印场景用；`px` 本身是 CSS 逻辑像素而不是物理像素，高分屏上 1px 会对应多个物理像素。
>
> 相对单位里，字体相关的有 `em`、`rem`、`ex`、`ch`、`lh`，视口相关的有 `vw`、`vh`、`vmin`、`vmax` 以及移动端更可靠的 `svh` / `lvh` / `dvh`，容器查询相关的是 `cqw` / `cqh` / `cqi`，另外还有百分比 `%`。
>
> 实践中字号用 `rem`（无障碍）、组件内相对尺寸用 `em`、全屏高度用 `dvh`、流体排版用 `clamp()` 配 `vw`。需要注意 `em` 会随嵌套逐级放大，垂直方向的 `padding` 百分比参照的是父元素宽度，这两个是最常见的坑。

## 7. 详解：`line-height` 带不带单位到底差在哪

### 先破除一个误解

**在写法所在的那个元素上，`1.5`、`150%`、`1.5em`、`24px` 的渲染结果完全相同**——都是 24px（假设 `font-size: 16px`）。所以你在自己的元素上看不出任何区别，DevTools 的 Computed 面板里也都显示 `24px`。

**区别只发生在「继承」这一步**：这几种写法传给子元素的东西不一样。

| 写法 | 元素自身算出的行高 | **子元素继承到的是什么** | 子元素字号变大后 |
| --- | --- | --- | --- |
| `line-height: 1.5`（数字） | 24px | **数字 `1.5` 本身** | 按子元素自己的字号重新计算 → 等比放大 ✅ |
| `line-height: 150%` | 24px | 算好的 **24px** | 不跟随 → 挤压 ⚠️ |
| `line-height: 1.5em` | 24px | 算好的 **24px** | 不跟随 → 挤压 ⚠️ |
| `line-height: 24px` | 24px | 固定的 **24px** | 不跟随 → 挤压 ⚠️ |
| `line-height: normal` | 由字体度量决定（≈1.2） | 关键字 `normal` | 跟随，但具体倍数由字体决定，不可控 |

关键区别就一句：**无单位时继承的是「比例」，有单位/百分比时继承的是「算好的绝对值」**。这是 `line-height` 在所有 CSS 属性里独一无二的继承行为。

### 一个会踩坑的例子

```css
.card {
  font-size: 16px;
  line-height: 1.5em;   /* 在 .card 上算出 24px，并把 24px 继承下去 */
}

.card .title {
  font-size: 32px;      /* 字号翻倍 */
}
```

`.title` 继承到的行高仍然是 **24px**，但它的字号是 32px——**行高比字号还小 8px**，文字会明显上下挤压甚至重叠。

换成无单位数字：

```css
.card {
  font-size: 16px;
  line-height: 1.5;     /* 只把数字 1.5 继承下去 */
}

.card .title {
  font-size: 32px;      /* 行高自动变成 1.5 × 32 = 48px ✅ */
}
```

子元素拿到的是「1.5 这个倍数」，用自己的字号一乘就得到了合适的行高——**永远保持 1.5 倍的行距**。

### 为什么推荐全局写无单位

```css
body { line-height: 1.5; }   /* 全站把「行高 = 1.5 倍字号」这条规则传下去 */
```

这样任何子元素无论怎么改字号，行距都自动保持比例。反过来，如果写 `body { line-height: 24px }`，所有后代都被钉死在 24px，标题一大就挤。

### 什么时候**应该**用带单位的

不是带单位就错，少数场景反而是刻意要「不跟随」：

- **固定高度控件的垂直居中**：`height: 40px; line-height: 40px;`——这里的 `line-height` 是当居中的工具用，就是要固定值。
- **需要严格对齐的表格 / 列表**：希望所有行高统一，不随字号浮动。
- **图标与文字基线对齐**：需要精确的像素级控制时。

### 补充：`normal` 为什么不推荐算作方案

`line-height: normal` 的值取决于**字体自身的度量信息**（不同字体的升部、降部、行间隙不同），中文和英文字体混排时能差出 0.1~0.2。所以它「看着还行」，但你没法精确预测最终数值，跨字体、跨平台也不一致。要可控就显式写数字。

### 一句话记忆

> **`line-height` 写数字，继承的是「倍数」；写单位或百分比，继承的是「算完的像素值」。** 想让它跟着字号一起缩放，就别带单位。
