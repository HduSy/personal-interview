# 04. 设备像素、CSS 像素、设备独立像素、DPR、PPI 之间的区别？

## 1. 先看一张关系图

这五个概念分成**硬件层**和**软件层**两组，弄清「谁换算成谁」就全通了：

<Mermaid chart={`
flowchart LR
    CSS["CSS 像素<br/>代码里写的 px"] -->|"× DPR"| DEV["设备像素<br/>屏幕上的发光点"]
    DEV -->|"÷ PPI"| PHY["物理尺寸<br/>英寸 / 毫米"]
    PPI["PPI<br/>= 像素数 ÷ 对角线英寸"] -.->|"描述密度"| DEV
    DIP["设备独立像素<br/>Android dp / iOS pt"] -.->|"100% 缩放下 1:1"| CSS
`} />

一句话概括：**PPI 描述硬件有多密，设备像素是硬件的最小单位，CSS 像素和设备独立像素是软件层的抽象单位，DPR 是两者之间的换算比例。**

## 2. 逐个拆解

### (1) 设备像素（Device Pixel）——也叫物理像素

- **屏幕硬件上的最小物理单元**，一个能独立发光的点。
- **出厂即固定，不可改变**。手机参数里的「分辨率 1179 × 2556」说的就是设备像素的数量。
- 它是**硬件属性**，和 CSS、和代码都没有关系。

### (2) CSS 像素（CSS Pixel）——Web 的逻辑像素

- **CSS 代码里写的 `px`**，是一个抽象的长度单位，不直接对应任何物理发光点。
- 规范把它定义为**参考像素**：在约 28 英寸观看距离上，1px 的视角约为 1/96 英寸——目的是让同样的 `px` 在不同屏幕上**看起来差不多大**。
- 它和物理像素的比例随时会变：换设备会变，**浏览器缩放（Ctrl/Cmd +）也会变**（详见 [03. CSS 中的像素单位](/css/03-css-length-units)）。
- 一个 CSS 像素对应多少个物理像素，由 **DPR** 决定。

### (3) 设备独立像素（Device-Independent Pixel，DIP）

- **跨平台通用的抽象概念**：一种与具体硬件解耦的长度单位，保证相同数值在不同设备上物理尺寸接近。
- 各平台有自己的实现：**Android 的 `dp`**（1dp = 1/160 英寸）、**iOS 的 `pt`**（point）、**Web 的 CSS 像素**。
- 所以严格说：**CSS 像素是「设备独立像素」在 Web 平台上的具体实现**。在 100% 缩放下，二者可以视为 1:1 的同一个东西；但提到「设备独立像素」时，很多资料特指移动端的 dp。

### (4) DPR（Device Pixel Ratio）——设备像素比

- **一个比值，不是一种像素**：

  ```
  DPR = 设备像素 / CSS 像素   （只看一个方向）
  ```

- `window.devicePixelRatio` 可以读，常见值：普通屏 `1`，Retina 屏 `2` 或 `3`。
- `DPR = 2` 时，1 个 CSS 像素覆盖 2 × 2 = **4 个**物理像素（面积是 4 倍）。
- **会随浏览器缩放变化**：在 DPR = 2 的屏幕上把页面放大到 200%，`devicePixelRatio` 会变成 4。

### (5) PPI（Pixels Per Inch）——像素密度

- **每英寸屏幕上的物理像素数量**，纯硬件指标。最直观的理解是「**同一条对角线上，量两遍再相除**」：

  ```
  PPI = 对角线上的像素数 ÷ 对角线的物理长度（英寸）
  ```

  对角线上的像素数用勾股定理算出来，就得到常见的展开写法：

  ```
  PPI = √(水平像素² + 垂直像素²) ÷ 屏幕对角线英寸数
  ```

  两种写法**完全等价**：分子是「对角线有多少个物理像素」，分母是「对角线有多少英寸」。

  之所以能用对角线来算，是因为**像素是正方形**——横向、纵向、斜向量出来的密度都相等（`水平像素÷水平英寸 = 垂直像素÷垂直英寸 = 对角像素÷对角英寸`），所以任选一个方向结果都一样，而对角线恰好是唯一能直接从厂商标称尺寸拿到的量。

- 例：
  - 24 英寸 1920×1080 显示器：√(1920² + 1080²) ÷ 24 ≈ **92 PPI**（普通屏，DPR = 1）
  - 6.1 英寸 1179×2556 手机：√(1179² + 2556²) ÷ 6.1 ≈ **461 PPI**（高清屏，DPR = 3）
- PPI 和 CSS 无关，**它只描述硬件**。同尺寸屏幕上像素越多，PPI 越高，画面越细腻。

> **「对角线英寸」不是面积单位**：英寸是**长度单位**（1 inch = 2.54 cm），「6.1 英寸屏幕」说的是**对角线长度**是 6.1 英寸——一维的线段长度，不是面积（面积要用平方英寸）。所以公式里 `÷ 屏幕对角线英寸数` 才成立：对角线像素数 ÷ 对角线物理长度 = 每英寸多少个物理像素。
>
> 而且**同样对角线下，宽高比不同，实际面积也不同**。对角线为 `d`、宽高比为 `k`（宽 ÷ 高）的矩形，面积 = `d² · k / (1 + k²)`——比值越接近 1（越接近正方形）面积越大。举例：6.1 英寸的 **4:3** 屏比 6.1 英寸的 **16:9** 屏面积大约 **12%**。这也是为什么手机屏幕「从 5.5 英寸变成 6.1 英寸」时，握持感的变化并不成比例。
>
> 用对角线描述屏幕大小是沿袭 CRT 显像管时代的惯例：**一个数字概括大小**，再配合宽高比才能确定实际面积。

## 3. 对比表

| 概念 | 所属层面 | 是否可变 | 由谁决定 | 单位 / 公式 |
| --- | --- | --- | --- | --- |
| **设备像素** | 硬件 | 固定 | 屏幕出厂规格 | 个 |
| **CSS 像素** | 软件 / 规范 | 随缩放变化 | 浏览器 | `px` |
| **设备独立像素** | 软件 / 平台抽象 | 基本固定 | 操作系统 / 平台 | `dp`（Android）、`pt`（iOS） |
| **DPR** | 换算比例 | 随缩放变化 | 浏览器 / 系统 | 设备像素 ÷ CSS 像素 |
| **PPI** | 硬件 | 固定 | 屏幕物理属性 | √(w² + h²) ÷ 对角线英寸 |

## 4. 五个概念怎么串起来

```
屏幕尺寸（英寸） + 分辨率（设备像素）  →  PPI（硬件密度）
                                      ↓
                           厂商/系统据此设定 DPR
                                      ↓
              CSS 像素 × DPR = 设备像素   →  再 ÷ PPI = 物理尺寸
```

**为什么需要 DPR？** 因为高 PPI 屏幕上如果让 1 CSS 像素 = 1 设备像素，文字会小到看不清（461 PPI 的屏幕上，16px 的文字只有几毫米）。所以系统设定 DPR，让 1 CSS 像素覆盖多个物理像素，既保证**物理尺寸合理**，又利用多出来的像素提升**清晰度**。

DPI 与 DPR 的关系（粗略）：`DPR ≈ PPI / 基准密度`。Web 的基准约为 96（对应参考像素），Android 的 dp 基准是 160。这只是**近似关系**——DPR 最终是厂商和浏览器根据 PPI 与观看距离人为设定的整数，不是严格算出来的。

## 5. 工程意义：这些概念到底影响什么

### (1) 1px 边框为什么在高分屏上显得粗 / 糊

DPR = 2 时，1 CSS 像素 = 2 个物理像素。想要「真正的 1 物理像素细线」，得写 `0.5px`（部分浏览器支持），或用伪元素 + `transform: scaleY(0.5)`。

### (2) 图片为什么要 1x / 2x / 3x

一张 100×100 CSS 像素的图片，在 DPR = 3 的屏幕上需要 300×300 的**物理像素**才清晰。用 `srcset` 让浏览器按 DPR 选择（详见 [07. img 的 srcset](/html/07-img-srcset)）。

### (3) Canvas 必须按 DPR 放大缓冲区

`canvas.width` 的单位是**设备像素**，CSS 尺寸的单位是 **CSS 像素**。不按 DPR 放大，画出来的图会糊——这就是 `ctx.scale(dpr, dpr)` 的由来（详见 [13. Canvas 与 SVG](/html/13-canvas-vs-svg)）。

### (4) 设计稿换算

- 标注为 **750px 宽（@2x）** 的移动端设计稿 → CSS 宽度按 `750 ÷ 2 = 375px` 写。
- 标注为 **1125px（@3x）** → 除以 3。
- 判断设计稿倍数的方法：看稿子的宽度比例，或直接问设计师。**用错倍数，整套尺寸就会差一半或三分之一**。

### (5) 媒体查询区分高清屏

```css
@media (min-resolution: 2dppx) {
  /* DPR >= 2 时生效 */
}
```

`dppx` 就是 DPR 的 CSS 单位，比老写法 `-webkit-min-device-pixel-ratio` 更标准。

## 6. 四个常见混淆

- **「DPR 就是缩放比例」** —— 不是。DPR 是设备像素与 CSS 像素的比值；浏览器缩放会影响它，但系统缩放、屏幕本身的 DPR 是独立设定的。
- **「PPI 和 DPR 是一回事」** —— 不是。PPI 是纯硬件密度，DPR 是软件层的换算比例，二者相关但不等价。
- **「设备独立像素就是设备像素」** —— 正好相反，前者是抽象的逻辑单位，后者是物理发光点。
- **「CSS 像素永远是 1:1 对应设备独立像素」** —— 在浏览器缩放 100% 时成立，缩放后会脱钩。

## 7. 面试速答版

> **设备像素**是屏幕硬件上的最小物理发光单元，出厂固定；**PPI** 是每英寸的物理像素数，由分辨率和对角线尺寸算出，是纯硬件指标。
>
> **CSS 像素**是代码里写的 `px`，是软件层的抽象单位，规范定义为参考像素，目的是让不同屏幕上的视觉大小接近；**设备独立像素**是更通用的跨平台抽象概念，Android 的 dp、iOS 的 pt 都是它的实现，CSS 像素可以理解为它在 Web 上的具体形式。
>
> **DPR** 是设备像素与 CSS 像素的比值，DPR = 2 时 1 个 CSS 像素覆盖 4 个物理像素，它同时受屏幕和浏览器缩放影响。
>
> 实践影响主要是三块：高分屏的 1px 边框、图片要提供 2x/3x 资源、Canvas 要按 DPR 放大缓冲区；另外设计稿标注 750px 时要除以 2 换算成 CSS 像素。

## 8. 详解：为什么浏览器缩放也会改变 DPR

### 一句话：缩放没有改变屏幕，改变的是「一个 CSS 像素要吃掉几个设备像素」

按下 Ctrl/Cmd + 放大页面时，**物理屏幕一个像素都没多**，但浏览器决定「把每个 CSS 像素画得更大」——于是同一个 CSS 像素要占用更多设备像素，比值 DPR 自然就变大了。

### 具体推演

假设一台 14 英寸笔记本：物理分辨率 3024 × 1964 设备像素，硬件 DPR = 2，所以布局视口宽度是 `3024 ÷ 2 = 1512` CSS 像素。

| 页面缩放 | 布局视口宽度（CSS 像素） | 1 个 CSS 像素占几个设备像素 | `devicePixelRatio` |
| --- | --- | --- | --- |
| 100% | 1512 | 2 | **2** |
| 150% | ≈ 1008 | 3 | **3** |
| 200% | 756 | 4 | **4** |

可以看到：**屏幕宽度（设备像素）始终是 3024，但布局视口（CSS 像素）在不断缩小**。浏览器为了把那 756 个 CSS 像素铺满 3024 个设备像素，只能让每个 CSS 像素占 4 个设备像素——这就是 DPR 变大的原因。

公式：

```
当前 devicePixelRatio = 硬件 DPR × 页面缩放倍数
```

### 为什么要这样设计

因为 CSS 像素被定义成一个**有物理感的单位**（参考像素），它的职责是「在不同设备上看起来差不多大」。既然用户主动要放大，浏览器就必须让每个 CSS 像素渲染得更大——这在实现上就等于提高 DPR。

反过来看也说得通：如果缩放后 DPR 不变，那页面就只是「显示更多/更少的 CSS 像素」，内容大小不会变，缩放功能就失效了。

### 一个副作用：缩放会像「屏幕变小」一样触发响应式

因为媒体查询判断的是 **CSS 像素**，放大页面后视口 CSS 宽度变小：

```css
@media (max-width: 768px) { /* 放大到一定程度会命中，布局切换成移动端 */ }
```

这不是 bug，是**无障碍设计的一部分**——低视力用户放大页面时，正好得到大字号、单列的移动端布局。

### 工程影响

**(1) Canvas 会糊**

很多代码只在初始化时读一次 DPR：

```js
// ❌ 用户缩放后就糊了，因为缓冲区还是按旧 DPR 建的
const dpr = window.devicePixelRatio;
canvas.width = cssWidth * dpr;

// ✅ 每次变化都重新设置
function setupCanvas() {
  const dpr = window.devicePixelRatio;
  canvas.width = canvas.clientWidth * dpr;
  canvas.height = canvas.clientHeight * dpr;
  ctx.setTransform(dpr, 0, 0, dpr, 0, 0);
}
window.addEventListener('resize', setupCanvas);   // 缩放会触发 resize
```

更精确的监听方式是用 `matchMedia`：

```js
let mq;
function watchDpr() {
  mq?.removeEventListener('change', onChange);
  mq = matchMedia(`(resolution: ${window.devicePixelRatio}dppx)`);
  mq.addEventListener('change', onChange);
}
function onChange() { setupCanvas(); watchDpr(); }  // DPR 变了要重新绑定
```

**(2) `srcset` 图片会被重新选择**

浏览器会把 DPR 计入图片选择逻辑，放大后可能去拉更高分辨率的图——这是预期行为，别奇怪。

**(3) 1px 边框的观感变化**

缩放 200% 时 1 CSS 像素 = 4 个设备像素，「细线」在视觉上会变粗。

### 三种「缩放」要分清

| 类型 | 触发方式 | 对 `devicePixelRatio` 的影响 |
| --- | --- | --- |
| **页面缩放（page zoom）** | 桌面端 Ctrl/Cmd + / - | ✅ 会变，`硬件 DPR × 缩放倍数` |
| **系统缩放** | 操作系统显示设置（如 Windows 125%） | ✅ 会变，属于「硬件 DPR」的一部分 |
| **双指捏合（pinch zoom）** | 移动端手势 | ❌ 一般不变，变化的是 `visualViewport.scale`（视觉视口） |

第三种容易混：移动端捏合放大的是「视觉视口」，页面布局（CSS 像素与布局视口）并没有重新计算，所以 DPR 通常保持原值。桌面端的页面缩放则是真正重新计算布局的。

### 一句话回答面试官

> 因为缩放改变的是「1 个 CSS 像素映射到多少个设备像素」。屏幕的设备像素总数固定，页面放大后布局视口（CSS 像素）变小，浏览器必须让每个 CSS 像素占更多设备像素才能铺满屏幕，所以 `devicePixelRatio = 硬件 DPR × 缩放倍数` 会变大。这也顺带解释了为什么放大页面会触发媒体查询——媒体查询判断的是 CSS 像素宽度。
