# 19. 布局适配的详细方案有哪些？

## 高频问答

### 1. 面试官：布局适配的详细方案有哪些？

**回答**：布局适配的方案分两类，选错流派后面全是补丁：

- **等比缩放**：整页按视口宽度等比放大缩小，保持与设计稿一致的视觉比例——适合**视觉型页面**（H5 活动页、营销页），设计稿是什么样，每台手机上就是什么样；
- **内容自适应（流式）**：布局随空间流动、内容重排，不追求等比——适合**内容型页面**（官网、文档、后台），保证的是可读性不是比例。

缩放类的三个方案是 rem + 动态根字号、vw、整体 scale；内容自适应用 % + Flex/Grid + 媒体查询。流式与媒体查询、容器查询在[响应式题](/css/13-responsive-design)里详细讲过，本题重点讲等比缩放流派。

### 2. 面试官：rem + 动态根字号方案是怎么做的？

**回答**：原理：`rem` 参照根字号 → 按屏宽动态设置 `html` 的 `font-size` → 全部尺寸用 `rem`，页面随视口整体等比。

```js
// flexible 的做法：屏宽 10 等分，750 设计稿下 1rem = 75px
document.documentElement.style.fontSize =
  document.documentElement.clientWidth / 10 + 'px';
```

纯 CSS 等价写法，连 JS 都省了：

```css
html { font-size: calc(100vw / 10); }
```

工程上不手写 rem，构建时用 postcss-pxtorem 自动换算，开发仍然按设计稿 px 写：

```js
// postcss.config.js
'postcss-pxtorem': { rootValue: 75, propList: ['*'] }  // 750 设计稿
```

这是手淘 flexible 库时代的标准方案，vw 普及后已被替代，存量项目仍大量存在。

### 3. 面试官：vw 方案呢？正文文字要不要跟着等比？

**回答**：`1vw` = 视口宽的 1%，纯 CSS 实现等比，是现行主流。设计稿 750px 时，1px 设计稿值 = 100/750 vw，构建时 postcss-px-to-viewport 自动换算，开发照旧写 px：

```js
// postcss.config.js
'postcss-px-to-viewport': { viewportWidth: 750 }
```

它取代 flexible 的原因：flexible 用 JS 动态根字号模拟的东西，`vw` 原生就是——主流浏览器全面支持 vw 后，模拟层失去意义，flexible 官方也建议直接用 vw 适配。优点：不依赖根字号、不依赖 JS。两个坑：

1. **极端屏等比过头**：iPad、折叠屏上文字被等比放到巨大——关键尺寸配 `clamp()` 限幅（clamp 流体写法[响应式题](/css/13-responsive-design)讲过）；
2. **PC 上 `100vw` 含滚动条宽度**，大于可视区会撑出横向滚动条——PC 端布局用 `%`，或按平台区分单位。

文字要不要跟着等比：布局等比、可读性优先——正文常用固定档位或独立媒体查询，只对间距、图形用缩放单位。等比把 375 屏的 12px 正文带到 iPad 上会变成约 25px，反之小屏会压到不可读（[最小字号题](/css/15-font-size-below-12px)讲过）。

### 4. 面试官：内容型页面用什么方案？

**回答**：百分比 + Flex/Grid，让布局「流动」而不是「缩放」：`%` 相对父级、flex/grid 分配剩余空间、`min/max` 约束极值，空间不够时内容换行重排。适合内容型页面的原因：正文文字等比缩放后在极端屏不可读，重排才能同时兼顾小屏与大屏。与等比方案的取舍：**视觉还原选 vw，信息可读选流式**。

### 5. 面试官：数据可视化大屏怎么适配？

**回答**：按固定设计稿（如 1920×1080）写死 px，运行时按实际分辨率整体缩放：

```js
const screen = document.querySelector('.screen');
const scale = Math.min(innerWidth / 1920, innerHeight / 1080);
screen.style.transform = `scale(${scale})`;
screen.style.transformOrigin = 'left top';
```

优点：还原度 100%，开发按固定稿写；缺点：非整数倍缩放文字发虚、事件坐标要按缩放比换算。大屏也可用 vw 方案逐元素缩放。

### 6. 面试官：刘海屏和底部横条怎么处理？

**回答**：`viewport-fit=cover` 声明延伸到安全区外，再用 `env(safe-area-inset-top/bottom)` 把关键内容从危险区推开。

### 7. 面试官：能总结一下吗？

**回答**：一张表收尾：

| 方案 | 流派 | 依赖 | 典型场景 |
| --- | --- | --- | --- |
| rem + 动态根字号 | 等比 | JS 或 `calc` + 构建插件 | H5（历史主流） |
| vw + postcss | 等比 | 构建插件 | H5（现主流） |
| % + Flex/Grid + 媒体查询 | 自适应 | 无 | 官网 / 文档 / 后台 |
| `transform: scale` | 整页缩放 | JS | 数据可视化大屏 |

一句话选型：**视觉型页面 vw，内容型页面流式，大屏 scale，rem 是存量**。

## 加深理解

### 为什么等比缩放不适合内容型页面

等比保比例不保可读性：同一版式从 320px 手机等比放到 1280px 桌面，文字、留白全部翻四倍，一屏能读的信息量骤降；缩到小屏则文字小于可读下限。内容型页面的正确响应是**重排**——两栏变单栏、字号走 `clamp` 限幅——而不是把同一张版式整体缩放。视觉型页面（海报式 H5）没有阅读密度问题，才适合等比。

### calc(100vw / 10) 与 flexible 的 JS 有差别吗

效果上没有：两者都是「根字号 = 视口宽 / 10」。flexible 库没有被简化成这一行 CSS，是因为它还附带 DPR 处理（按 `devicePixelRatio` 缩放 viewport 应对高清屏 1px 问题）——后来这套 viewport 缩放策略本身被放弃（副作用大于收益），库随之整体退役，剩 `calc` 一行就是它的全部遗产。
