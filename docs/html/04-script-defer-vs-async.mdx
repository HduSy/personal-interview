# 04. script 标签中 defer 和 async 的区别

## 1. 为什么需要 defer 与 async？（默认 script 的阻塞机制）

默认情况下，当浏览器 HTML 解析器遇到 `<script src="...">` 时，会**立即停止（阻塞）HTML 解析**：
1. 暂停 DOM 树的构建；
2. 发起网络请求下载该外部脚本；
3. 下载完成后立即执行脚本；
4. 脚本执行完毕后，才继续向下恢复 DOM 解析。

这种机制被称为**解析阻断（Parser-Blocking）**。若脚本体积过大或网络延迟较高，会导致首屏长时间处于白屏状态。传统方案往往将脚本置于 `<body>` 最底部，但这会推迟脚本的下载时机。

为了解决这一痛点，HTML5 提供了两个布尔属性：**`defer`（推迟）** 与 **`async`（异步）**。

## 2. defer 与 async 的核心区别

两者的共同点是：**脚本的网络下载过程都是异步并行的，绝不阻塞 HTML 的解析过程**。

核心差异在于两个关键维度：**执行时机** 与 **执行顺序保证**。

### 核心特性对比表

| 特性维度 | 普通 `<script>` | `<script defer>` | `<script async>` |
| --- | --- | --- | --- |
| **脚本下载** | 遇到即刻发起，**阻塞 HTML 解析** | 异步并行下载，**不阻塞 HTML 解析** | 异步并行下载，**不阻塞 HTML 解析** |
| **脚本执行时机** | 下载完成后**立即执行**，执行期间阻塞解析 | 等到 **HTML 完全解析完毕**、在 `DOMContentLoaded` 事件触发**前**执行 | 只要**下载完成就立即中断 HTML 解析并执行**，执行完毕后恢复解析 |
| **多脚本执行顺序** | 严格按照 HTML 文档中的**书写顺序**执行 | 严格保证按照 HTML 文档中的**书写顺序**依次执行 | **乱序执行**：谁先下载完成谁先执行，完全取决于网络耗时 |
| **与 DOMContentLoaded 的关系** | 阻碍事件触发 | 保证在 `DOMContentLoaded` 触发**之前**全部执行完成 | **不确定**：可能在 `DOMContentLoaded` 触发之前或之后执行 |
| **典型适用场景** | 遗留代码（通常置于 `<body>` 底部） | 依赖完整 DOM 树、或存在上下文依赖关系的业务核心脚本（如主应用 bundle） | 独立运行、不依赖 DOM 也不被其他脚本依赖的脚本（如埋点、Google Analytics、广告 SDK） |

## 3. 进阶延伸：type="module" 的行为

现代前端普遍采用的 ES 模块脚本（`<script type="module" src="...">`）：
- **默认具备 `defer` 的行为**：在后台异步并行下载，待整个 DOM 文档解析完成后、在 `DOMContentLoaded` 触发前按标签顺序依次执行。
- **若显式添加 `async` 属性**（`<script type="module" async src="...">`）：则行为转变为 `async`，即模块及其所有依赖项一旦全部下载编译完毕，便立即中断主线程执行。

## 你的回答

浏览器在解析 HTML 标签时是从上到下执行的。遇到默认的 script 脚本，解析会停下来等待 JS 的加载，解析执行之后才会恢复 HTML 的解析和 DOM 的构建。在这期间屏幕是白屏的，存在大量的白屏时间。

defer 和 async 都可以让浏览器并行下载 JS，而不用阻塞 HTML 的解析。它们的主要区别如下：

1. 代码执行时机：
   - defer：会等到浏览器的 DOM 构建完成时才会去执行。
   - async：一旦 JS 下载完成就会立马执行，会打断 HTML 的解析过程。这就是它们在代码执行时机上的区别。

2. 执行顺序：
   - defer：同时声明 defer 属性的脚本，会按声明顺序依次执行。
   - async：声明多个 async 属性的 script 标签，哪个优先下载完成，哪个就第一个执行。

3. 适用场景：
   - defer：适合有依赖关系的脚本声明。比如主 bundle（如 React JS），要先加载完成，才能执行业务的 JS。
   - async：比较适用于独立的脚本。比如打点、埋点上报脚本，或者 Google Ads 等这样的脚本。
