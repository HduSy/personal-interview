# 11. iframe 有哪些优点和缺点？

## 1. 是什么与优点

iframe 是嵌套浏览上下文，内部有独立的 `window`、`document`、DOM、样式、JS 和 history。

| 属性 | 作用 |
| --- | --- |
| `src` | 被嵌入文档的 URL |
| `srcdoc` | 直接用一段 HTML 字符串作为文档内容，优先级高于 `src` |
| `sandbox` | 限制子文档的能力（最核心的安全开关） |
| `allow` | 权限策略（Permissions Policy），控制摄像头、麦克风、全屏等 |
| `loading="lazy"` | 视口外的 iframe 延迟加载 |
| `title` | 无障碍名称，**必填**（无障碍规范要求） |
| `referrerpolicy` | 控制请求子资源时的 Referer 信息 |

核心优势是文档级隔离和零集成成本：

- **隔离最彻底**：父页面 CSS 无法命中内部元素，样式不外泄；全局变量、定时器互不干扰。需要 JS 全局隔离时基本只能用 iframe。

  | 方案 | DOM 隔离 | 样式隔离 | JS 全局隔离 |
  | --- | --- | --- | --- |
  | **iframe** | ✅ 独立文档树 | ✅ 完全隔离 | ✅ 独立 `window` |
  | **Shadow DOM** | ✅ 影子树 | ✅ 样式作用域 | ❌ 共享同一个 `window` |
  | **CSS Module / Scoped** | ❌ | ⚠️ 仅局部分隔 | ❌ |

- **天然的安全边界**：不同源受同源策略保护，父子读不到对方 DOM 与存储，只能 `postMessage` 通信；`sandbox` 可压低权限。
- **接入第三方成本最低**：广告、地图、视频、支付只需一个 URL，无需 SDK 或构建集成。
- **承载异构与遗留应用**：老系统可整块嵌入；微前端也依赖 iframe 做隔离。
- **声明式能力**：`loading="lazy"` 延迟加载；`srcdoc` + `sandbox` 做代码沙箱预览；`allow` 按需开放设备权限。

## 2. 缺点

缺点集中在性能、SEO、可访问性、布局、通信和调试。

- **性能开销大**：每个 iframe 是完整文档，有独立渲染树和 JS 上下文；同源 iframe 与父页面共享渲染进程，繁重 JS 拖慢主线程；跨源独立进程，占用更高；还会推迟 `window.load`。
- **SEO 不友好**：内容归属被嵌入的 URL，父页面拿不到权重，爬虫抓取不稳定，正文不能放 iframe。
- **可访问性差**：屏幕阅读器在边界出现上下文断层，必须加 `title`。
- **布局割裂**：高度无法自适应，需 `postMessage` / `ResizeObserver` 回传；`position: fixed` 相对 iframe 视口，弹窗错位；滚动、全屏受限。
- **跨域通信困难**：跨域只能 `postMessage`，要校验 `event.origin`；第三方 Cookie 与存储分区让登录态、埋点难维持。
- **调试成本高**：跨源日志受限；SPA 中 iframe 路由会与 history 冲突。

## 3. 安全风险与防护

安全风险双向存在：

- **向外**：嵌入不可信来源，钓鱼、诱导点击由你承担。
- **向内**：被别人的 iframe 套住会发生点击劫持，用 `X-Frame-Options` 或 `frame-ancestors` 防御。
- 其他攻击面：`window.name` 跨域残留、`document.domain` 放宽同源也是攻击面。

`sandbox` 是最有效的限制：

```html
<!-- 失效条件：同时给 allow-scripts 与 allow-same-origin，且父子同源时，脚本可操作父页面 DOM，沙箱失效 -->
<!-- 空值 = 开启全部限制：子文档变成不透明源，脚本/表单/弹窗/顶层跳转全部禁止 -->
<iframe src="https://third-party.example" sandbox title="第三方内容"></iframe>

<!-- 按需放开：只允许脚本与表单 -->
<iframe src="https://third-party.example" sandbox="allow-scripts allow-forms" title="第三方内容"></iframe>
```

同时给 `allow-scripts` 与 `allow-same-origin` 且同源时，沙箱失效。

`postMessage` 必须双向校验：

```js
// 父页面发送：第二个参数不要写 '*'，明确指定目标源
iframe.contentWindow.postMessage({ type: 'theme', value: 'dark' }, 'https://child.example');

// 父页面接收：先校验来源，再校验消息格式
window.addEventListener('message', (e) => {
  if (e.origin !== 'https://child.example') return;
  if (e.data?.type === 'resize') resizeIframe(e.data.height);
});
```

`targetOrigin` 不要写 `'*'`。

防点击劫持优先用 CSP：

```http
Content-Security-Policy: frame-ancestors 'self';
```

`frame-ancestors` 支持白名单；`X-Frame-Options` 只有固定值，兼容时同时下发；`frame-src` 方向相反。

## 4. 适用与不适用场景

iframe 用文档级隔离换取集成与性能成本，隔离需求到文档级别时才划算。

**适合**：第三方内容嵌入（广告、地图、支付、视频）、需要 JS 级隔离的微前端模块、遗留系统渐进迁移、代码沙箱预览、跨域但低耦合的独立子系统。

**不适合**：同站点内可组件化的 UI、需要 SEO 的正文内容、对首屏性能敏感的模块、需要高频父子交互的界面。

## 你的回答

iframe 提供了一种在父页面中嵌入子页面的能力，使其拥有独立的上下文（包括独立的 window、document 和 JS 运行上下文等）。

它的优点主要在于与父页面完全隔离。在子页面与父页面不同源的情况下，父子页面无法操作对方的 DOM，并且样式也不会相互污染。

它适用的场景，比如旧系统做迁移，可以在新的应用中通过 iframe 低成本地嵌入。

父子页面的通信方式主要是通过 postMessage 进行主动通信。需要强调的是，对 event.origin 做显式的判断会更加安全。

缺点也很多：

1. SEO 不友好。
2. 爬虫对 FM 的访问基本上不够稳定。
3. 比较占用资源开销。
4. 对无障碍不友好。
