# 11. iframe 有哪些优点和缺点？

## 1. iframe 是什么：一个嵌套的浏览上下文

`<iframe>`（inline frame）的作用是把**另一个完整的 HTML 文档**嵌入到当前页面中。它不是「一块可以放 HTML 的区域」，而是在页面里开了一个**嵌套浏览上下文（nested browsing context）**——iframe 内部拥有独立的 `window`、`document`、DOM 树、样式作用域、JS 全局环境和历史记录栈。

这个本质决定了一切优缺点：**隔离性来自「它是一份独立文档」，麻烦也来自「它是另一份独立文档」**。

关键属性速览：

| 属性 | 作用 |
| --- | --- |
| `src` | 被嵌入文档的 URL |
| `srcdoc` | 直接用一段 HTML 字符串作为文档内容，优先级高于 `src` |
| `sandbox` | 限制子文档的能力（最核心的安全开关） |
| `allow` | 权限策略（Permissions Policy），控制摄像头、麦克风、全屏等 |
| `loading="lazy"` | 视口外的 iframe 延迟加载 |
| `title` | 无障碍名称，**必填**（WCAG 要求） |
| `referrerpolicy` | 控制请求子资源时的 Referer 信息 |

## 2. 优点

### (1) 隔离最彻底——CSS / JS / 全局环境全独立

父页面的 CSS 选择器无法命中 iframe 内部元素，内部样式也不会外泄污染父页面；两边的全局变量、原型链、定时器、错误处理互不干扰。这是**隔离能力的天花板**：

| 方案 | DOM 隔离 | 样式隔离 | JS 全局隔离 |
| --- | --- | --- | --- |
| **iframe** | ✅ 独立文档树 | ✅ 完全隔离 | ✅ 独立 `window` |
| **Shadow DOM** | ✅ 影子树 | ✅ 样式作用域 | ❌ 共享同一个 `window` |
| **CSS Module / Scoped** | ❌ | ⚠️ 仅局部分隔 | ❌ |

只要需要「JS 也彻底隔离」，iframe 基本是唯一选择。

### (2) 天然的安全边界

不同源的 iframe 受**同源策略**保护：父页面读不到子文档的 DOM，子文档也读不到父页面的 DOM 与存储，两者只能通过 `postMessage` 显式通信。`sandbox` 属性还能把子文档的权限进一步压到最低（禁脚本、禁表单、禁弹窗、禁止与父页面同源等）。

### (3) 接入第三方内容成本最低

广告位、地图、视频播放器、支付收银台、客服组件、第三方登录、在线文档预览——对方只要给一个 URL 就能接，不需要任何 SDK 或构建集成，也天然避免了两边的样式与依赖冲突。

### (4) 承载异构与遗留应用

老系统渐进式迁移时，把旧模块直接嵌进新壳子是最省事的路径；不少微前端方案的「隔离模式」也仍然依赖 iframe 提供运行时沙箱。

### (5) 声明式的能力增强

`loading="lazy"` 让视口外的嵌入内容延迟加载；`srcdoc` 配合 `sandbox` 是代码沙箱预览（在线编辑器、Markdown 渲染预览）的经典做法；`allow` 按需开放摄像头、麦克风、全屏等能力，粒度可控。

## 3. 缺点

### (1) 性能开销大

- 每个 iframe 都是一份完整文档：独立的 Document、样式计算、渲染树、JS 上下文，内存与初始化成本远高于普通 DOM 节点。
- **同源 iframe 与父页面共享渲染进程**，内部的繁重 JS 会直接拖慢父页面的主线程；跨源 iframe 在启用站点隔离的浏览器里会**独立进程**，隔离性更好但资源占用更高。
- **iframe 的加载会推迟父页面 `window.load` 事件的触发**（不阻塞 `DOMContentLoaded`），把首屏指标拖后。用 `loading="lazy"` 可以缓解。

### (2) SEO 不友好

搜索引擎把 iframe 内的内容归属到**被嵌入的那个 URL**，而不是嵌入它的父页面。也就是说父页面拿不到这些内容的关键词权重，爬虫对 iframe 内内容的抓取也不稳定——正文内容绝不能放进 iframe。

### (3) 可访问性差

屏幕阅读器在 iframe 边界处会出现浏览上下文切换的断层，用户需要额外的操作才能进出。**必须给 iframe 提供 `title` 属性**描述其内容（WCAG 的硬性要求），否则读屏用户只会听到「框架」两个字。

### (4) 布局与交互割裂

- **高度无法自适应内容**：这是最经典的痛点，需要父页面用 `postMessage` 或 `ResizeObserver` 把子文档高度回传，再手动设置 iframe 高度。
- 子文档内的 `position: fixed` 是相对于 **iframe 视口**定位的，不是相对于整个页面，弹窗、吸顶栏、遮罩层都会错位。
- 滚动条、全屏、快捷键、右键菜单、跨边界的拖拽与选中，都受到不同程度限制。
- iframe 是**替换元素**，在层叠上下文里与普通元素行为不同，遮罩层覆盖其上偶有异常。
- 移动端上，iframe 的滚动与手势与父页面割裂，体验损耗明显。

### (5) 跨域通信困难

跨源只能靠 `postMessage` 传消息，且必须校验 `event.origin`，消息通道要自己设计（请求-响应、超时、序列化）。存储层面更麻烦：现代浏览器的**第三方 Cookie 限制**与**存储分区**，让 iframe 里的登录态、埋点、A/B 实验越来越难维持。

### (6) 安全隐患双向存在

- **向外**：嵌入不可信来源等同于把对方的内容当作自家页面的一部分展示，一旦对方页面被攻陷，钓鱼、诱导点击都会算在你头上。
- **向内（点击劫持）**：你的页面被别人的 iframe 套住，用户在透明层上点击实际触发了你的按钮——需要 `X-Frame-Options` 或 CSP 的 `frame-ancestors` 防御。
- 历史上的经典攻击面还有 `window.name` 跨域数据残留、`document.domain` 放宽同源（现已废弃并逐步移除）等。

### (7) 工程与调试成本

DevTools 需要在父页面与 iframe 之间切换执行上下文，跨源 iframe 的日志与网络请求查看受限；错误监控、埋点、性能指标（LCP、CLS 等）难以在父子之间统一收集；SPA 里 iframe 内部的路由还会和浏览器返回键、history 相互干扰。

## 4. 三条必须说清的安全实践

### (1) `sandbox` 是最有效的限制手段

```html
<!-- 空值 = 开启全部限制：子文档变成不透明源，脚本/表单/弹窗/顶层跳转全部禁止 -->
<iframe src="https://third-party.example" sandbox title="第三方内容"></iframe>

<!-- 按需放开：只允许脚本与表单 -->
<iframe src="https://third-party.example" sandbox="allow-scripts allow-forms" title="第三方内容"></iframe>
```

**致命坑**：同时给出 `allow-scripts` 与 `allow-same-origin` 时，若子文档与父页面同源，脚本可以直接操作父页面 DOM——沙箱等于失效。这两个值同时出现要格外谨慎。

### (2) `postMessage` 必须双向校验

```js
// 父页面发送：第二个参数不要写 '*'，明确指定目标源
iframe.contentWindow.postMessage({ type: 'theme', value: 'dark' }, 'https://child.example');

// 父页面接收：先校验来源，再校验消息格式
window.addEventListener('message', (e) => {
  if (e.origin !== 'https://child.example') return;
  if (e.data?.type === 'resize') resizeIframe(e.data.height);
});
```

`targetOrigin` 写成 `'*'` 等于把消息广播给任何当前加载在该 iframe 里的页面。

### (3) 防止被点击劫持，用 CSP 而不是只靠 X-Frame-Options

```http
Content-Security-Policy: frame-ancestors 'self';
```

`X-Frame-Options` 是更早的方案，只支持 `DENY` / `SAMEORIGIN` 等固定值；`frame-ancestors` 支持白名单且是现代标准，两者的推荐顺序是**优先 CSP，兼容性需要时同时下发**。另外 `Content-Security-Policy: frame-src` 控制你能嵌入哪些来源，方向相反，别搞混。

## 5. 什么时候用、什么时候别用

**适合用**：第三方内容嵌入（广告、地图、支付、视频）、需要 JS 级隔离的微前端模块、遗留系统渐进迁移、代码沙箱预览、跨域但低耦合的独立子系统。

**不适合用**：同站点内可组件化的 UI（用组件 + 样式隔离即可）、需要 SEO 的正文内容、对首屏性能敏感的模块、需要高频父子交互的界面（通信成本远高于收益）。

一句话总结：**iframe 是用「文档级隔离」换「集成与性能成本」的方案——隔离需求真的到文档级别时才划算。**

## 你的回答

iframe 提供了一种在父页面中嵌入子页面的能力，使其拥有独立的上下文（包括独立的 window、document 和 JS 运行上下文等）。

它的优点主要在于与父页面完全隔离。在子页面与父页面不同源的情况下，父子页面无法操作对方的 DOM，并且样式也不会相互污染。

它适用的场景，比如旧系统做迁移，可以在新的应用中通过 iframe 低成本地嵌入。

父子页面的通信方式主要是通过 postMessage 进行主动通信。需要强调的是，对 event.origin 做显式的判断会更加安全。

缺点也很多：

1. SEO 不友好。
2. 爬虫对 FM 的访问基本上不够稳定。
3. 比较占用资源开销。
4. 对无障碍不友好。
