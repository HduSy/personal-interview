# 13. Canvas 和 SVG 的区别？

## 1. 本质区别：位图 vs 矢量

这是所有其他差异的源头：

- **`<canvas>`** 是一块**位图画布**。它本身只有一个空白的像素缓冲区，所有图形都要通过 JS 调用绘图 API（`getContext('2d')` 或 WebGL）「画」上去，画完之后浏览器只记得**像素**，不记得「这里有一个圆」。
- **`<svg>`** 是一个**矢量图形容器**。它是基于 XML 的标记语言，每个形状都是真实的 DOM 节点（`<circle>`、`<path>`、`<rect>`），浏览器保存并维护整棵图形树。

前者是「一块画板」，后者是「一棵图形 DOM 树」。这一条决定了性能特征、交互能力、可访问性、缩放表现的全部差异。

## 2. 渲染模型：立即模式 vs 保留模式

| | Canvas（立即模式 Immediate Mode） | SVG（保留模式 Retained Mode） |
| --- | --- | --- |
| **数据结构** | 只有像素，没有图形对象 | 每个图形是一个 DOM 元素，可被查询、增删改 |
| **重绘方式** | 改一个图形要**清空整块画布重新画**，或自行实现局部重绘 | 改哪个元素的属性，浏览器自动做增量重渲染 |
| **状态管理** | 开发者自己维护（`save()` / `restore()` 只能救回绘图状态，救不回图形） | 浏览器维护，开发者操作 DOM 即可 |

一句话：**Canvas 里「图形」是你脑子里的概念，浏览器眼里只有像素；SVG 里图形是浏览器实实在在的对象。**

## 3. 全面对比

| 维度 | Canvas | SVG |
| --- | --- | --- |
| **图形类型** | 位图（栅格） | 矢量 |
| **缩放 / 高 DPI** | 放大会模糊；需手动按 `devicePixelRatio` 放大缓冲区并缩放绘图上下文 | 无损缩放，任意倍率都清晰 |
| **元素级交互** | ❌ 没有事件，点击「某个圆」需要自己写命中检测（hit test） | ✅ 直接在 `<circle>` 上绑 `click` |
| **样式控制** | 只能用 canvas 的绘图 API 设置颜色/线宽；CSS 只能作用于整个元素（透明度、filter、transform） | ✅ CSS 直接控制填充、描边、hover、过渡动画，`currentColor` 可继承主题色 |
| **动画** | JS 逐帧清空重绘（`requestAnimationFrame`），完全可控 | CSS 动画 / JS 改属性 / SMIL；元素一多会卡 |
| **性能拐点** | 图形**数量越多越有优势**（上万粒子仍流畅），适合高频重绘 | 元素数量到**千级**后 DOM 与样式计算开销明显，上万几乎不可行 |
| **内存** | 与画布像素尺寸成正比（大画布很吃内存，且有最大尺寸限制） | 与节点数量和路径复杂度成正比 |
| **可访问性** | ❌ 默认对读屏软件不可见，需要 fallback 内容 + ARIA | ✅ 文本是可读文本，可被选中、搜索、朗读 |
| **SEO** | 内容不被索引 | 文本内容可被索引 |
| **文本** | 能画文字，但不可选中、不可搜索、不可复制 | 真实文本，可选中可搜索 |
| **导出图片** | 简单：`toDataURL()` / `toBlob()` | 需序列化为字符串再转成图片，或走服务端 |
| **像素级操作** | ✅ `getImageData` / `putImageData`，做图像处理、滤镜、识别 | ❌ 无法直接操作像素 |
| **依赖** | 必须有 JS，禁用 JS 时一片空白 | 纯声明式，无 JS 也能渲染（静态部分） |
| **文件体积** | 与像素尺寸无关，代码量小 | 与图形复杂度成正比，简单图标极小，复杂图形很大 |

## 4. 两段必会的关键代码

### Canvas：别写出模糊的画布

```html
<canvas id="chart" style="width: 600px; height: 400px;"></canvas>
```

```js
const canvas = document.getElementById('chart');
const dpr = window.devicePixelRatio || 1;

// 关键：width/height 属性决定「像素缓冲区」大小，CSS 决定「显示尺寸」
const rect = canvas.getBoundingClientRect();
canvas.width = rect.width * dpr;
canvas.height = rect.height * dpr;

const ctx = canvas.getContext('2d');
ctx.scale(dpr, dpr);   // 之后按 CSS 像素坐标绘制即可，自动映射到高分辨率缓冲区
```

**最经典的坑**：`width`/`height` 属性与 CSS 尺寸混为一谈。属性不给就是默认 `300 × 150`，CSS 再拉大 → 像素被拉伸 → 图像模糊。高分屏上必须按 DPR 放大缓冲区。

### SVG：图形就是 DOM

```html
<svg viewBox="0 0 100 100" width="200" height="200" role="img" aria-label="进度环">
  <circle cx="50" cy="50" r="40" fill="none" stroke="#e5e7eb" stroke-width="8" />
  <circle class="progress" cx="50" cy="50" r="40" fill="none" stroke="#3b82f6"
          stroke-width="8" stroke-dasharray="251" stroke-dashoffset="63"
          transform="rotate(-90 50 50)" />
</svg>
```

```css
/* 直接用 CSS 控制图形，还能过渡动画 */
.progress { transition: stroke-dashoffset .3s ease; }
svg:hover .progress { stroke: #2563eb; }
```

`viewBox` 定义内部坐标系，`width`/`height` 决定显示尺寸——两者分离，所以可以任意缩放而不失真。

- **选 Canvas**：游戏、粒子 / 物理效果、大规模数据可视化（上万点位的散点图、实时曲线）、图像处理与滤镜、视频 / 摄像头帧处理、地图瓦片渲染引擎、白板绘图。
- **选 SVG**：图标系统（如今已全面取代 icon font）、Logo、可缩放插图、需要 hover 态与 CSS 动画的图形、节点数量可控且交互丰富的图表（如 D3 生成的组织图、流程图）、需要被读屏朗读或 SEO 的图形。
- **混合方案**：常见的工程折中是「Canvas 画海量静态图层 + DOM / SVG 叠一层交互层」。例如地图引擎用 Canvas 渲染瓦片，用 DOM 元素标注兴趣点；图表库（如 ECharts）同时提供 Canvas 与 SVG 两种渲染器，按数据量切换。

## 6. 高频追问

- **Canvas 怎么导出图片？** `canvas.toDataURL('image/png')` 或 `canvas.toBlob(cb)`。注意：画布被跨域图片「污染」过时会抛 `SecurityError`，需要图片服务支持 CORS 且 `img.crossOrigin = 'anonymous'`。
- **Canvas 怎么实现点击某个图形？** 浏览器不提供命中检测，得自己算：简单图形做几何判定（点在圆内 / 矩形内），复杂场景用**离屏颜色缓冲**（每个图形画成唯一颜色，读取点击位置像素反查 ID）或空间索引。
- **SVG 元素一多就卡，怎么办？** 减少 DOM 数量（路径合并、`<use>` 复用、虚拟化只渲染可视区），或者干脆换成 Canvas 渲染器。
- **Canvas 内容读屏读不到怎么办？** 在 `<canvas>` 标签内放 fallback 内容，外层加 `role="img"` 与 `aria-label`，另提供等价的数据表格或文字描述；复杂可视化建议直接提供「查看数据」的可访问替代视图。
- **内联 SVG 有安全风险吗？** 有。内联 SVG 中的 `<script>` 和事件属性会执行，嵌入**用户上传的 SVG** 前必须清洗；作为 `<img src>` 引入时脚本不会执行。

## 7. 详解：`ctx.scale(dpr, dpr)` 到底在做什么

### 两套坐标：缓冲区像素 vs CSS 像素

先记住一个前提：`<canvas>` 身上有**两个尺寸**，它们互不相同。

| 尺寸 | 由谁决定 | 单位 | 含义 |
| --- | --- | --- | --- |
| **像素缓冲区大小** | `canvas.width` / `canvas.height` **属性** | 设备像素（物理像素） | 真正存像素的内存有多大 |
| **显示尺寸** | CSS 的 `width` / `height` | CSS 像素 | 在页面上占多大地方 |

在 DPR = 2 的屏幕上，一个 CSS 像素由 2×2 个设备像素构成。为了让图形清晰，我们把缓冲区做成显示尺寸的 2 倍：

```js
canvas.width = 600 * dpr;    // DPR=2 → 1200，缓冲区 1200 设备像素宽
canvas.height = 400 * dpr;   // DPR=2 → 800
// CSS 上它依然显示为 600 × 400 CSS 像素
```

**问题来了**：缓冲区现在是 1200 宽，但显示区域仍然是 600 CSS 宽。也就是说，**缓冲区里的 1 个单位，在屏幕上只占 0.5 个 CSS 像素**。此时你写：

```js
ctx.fillRect(0, 0, 100, 100);   // 想画一个 100×100 的方块
```

实际会写入 100×100 个**设备像素**，显示到屏幕上只有 50×50 CSS 像素——**所有图形都缩水了一半**。

### `scale(dpr, dpr)` 的作用：把坐标系放大回去

Canvas 的 2D 上下文内部维护一个**变换矩阵（transformation matrix）**，所有绘图坐标（`x`、`y`、宽高、线宽、字体大小）在真正栅格化之前都要先过这个矩阵。

`ctx.scale(sx, sy)` 就是把当前变换矩阵**乘以**一个缩放因子。执行 `ctx.scale(2, 2)` 之后：

```js
ctx.scale(dpr, dpr);            // 变换矩阵变成 [2, 0, 0, 2, 0, 0]
ctx.fillRect(0, 0, 100, 100);   // 100×100 的坐标经过矩阵 → 实际写入 200×200 设备像素
                                // → 屏幕上正好是 100×100 CSS 像素 ✓
```

于是产生两种效果：

1. **尺寸对了**：你按 CSS 像素写坐标，画出来的东西在屏幕上的大小符合预期。
2. **清晰度保住了**：200×200 的设备像素被塞进 100×100 的 CSS 像素区域，每个 CSS 像素有 4 个设备像素的信息 → 细腻不糊。**分辨率没有变**，只是坐标换算被自动处理了。

一句话：**`scale` 不改变缓冲区，只改变「你写的数字如何映射到缓冲区」**。缓冲区是你在上一行用 `canvas.width` 撑大的，`scale` 负责让你不必在每次 `fillRect` 时手动乘 dpr。

### 三个必须注意的细节

**(1) 顺序不能颠倒——先设尺寸，再 scale**

给 `canvas.width` 或 `canvas.height` **赋任何值**（哪怕赋的是同一个值）都会**重置整个 2D 上下文状态**：变换矩阵、`fillStyle`、`lineWidth`、`font` 全部回到默认值。所以：

```js
ctx.scale(dpr, dpr);      // ❌ 先 scale
canvas.width = 600 * dpr; // 后赋值 → 变换被重置，缩放白做了
```

正确顺序永远是：**设 `width`/`height` → `getContext` → `scale`**。反过来说，每次 `canvas.width = ...` 之后都要**重新** `scale` 一次（同理，`fillStyle` 等也要重设）。

**(2) `scale` 是累乘的，`setTransform` 才是覆盖式的**

```js
ctx.scale(2, 2);
ctx.scale(2, 2);   // 现在实际是 4 倍，不是 2 倍
```

如果这段初始化逻辑可能被重复执行（比如窗口 resize 时重跑、但没重新赋值 `canvas.width`），缩放会**不断叠加**，图形越画越大。幂等的写法是用 `setTransform` 直接指定矩阵：

```js
ctx.setTransform(dpr, 0, 0, dpr, 0, 0);   // 绝对设置，重复调用结果不变
```

**(3) 线宽和文字会一起缩放**

变换矩阵作用于所有几何参数，`lineWidth = 2` 在 `scale(2,2)` 下会变成 2×2 设备像素 = 2 CSS 像素——**这正是我们想要的**（视觉粗细一致）。但如果你想要「无论怎么缩放，线始终是 1 物理像素」这种效果（比如某些图表要求发丝线），就不能靠 `scale`，得在绘制时按 dpr 反算线宽。

### 完整对照示例

```js
function setupCanvas(canvas, cssWidth, cssHeight) {
  const dpr = window.devicePixelRatio || 1;

  // 1. 先定缓冲区尺寸（这一步会重置上下文）
  canvas.width = cssWidth * dpr;
  canvas.height = cssHeight * dpr;
  canvas.style.width = cssWidth + 'px';    // 显示尺寸由 CSS 决定
  canvas.style.height = cssHeight + 'px';

  // 2. 再设置坐标系缩放（幂等写法）
  const ctx = canvas.getContext('2d');
  ctx.setTransform(dpr, 0, 0, dpr, 0, 0);

  return ctx;   // 之后所有绘制都按 CSS 像素写，例如 fillRect(10, 10, 100, 100)
}
```

### 等价说法（面试时怎么讲）

> 「`ctx.scale(dpr, dpr)` 放大的是**绘图坐标系**，不是画布本身。画布的物理像素尺寸是靠 `canvas.width = css 宽 × dpr` 撑大的；但那之后 1 个坐标单位只对应半个 CSS 像素，画出来的东西会缩小一半。`scale(dpr, dpr)` 相当于把变换矩阵乘以 dpr，让 `fillRect(0, 0, 100, 100)` 这类按 CSS 像素写的坐标自动映射到高分辨率缓冲区上——结果是尺寸正确、显示清晰，而代码不用到处乘 dpr。」

## 你的回答

Canvas 和 SVG 的最大区别在于：

1. **渲染原理与缩放表现**：
   Canvas 是基于像素的位图，随缩放大小而模糊；而 SVG 是基于 XML 语言的矢量图，不随缩放而受影响，因此后者常用于图标制作。

2. **绘制方式与 DOM 操作**：
   (a) Canvas：本质上是一块空白画布，有专门的 API，只能通过 JS 去绘制和填充。
   (b) SVG：是 DOM 元素，由非常多的 DOM 标签组成。它的 DOM 可以绑定 JS 事件，也可以通过 CSS 样式来影响。

3. **性能开销与适用场景**：
   (a) SVG：如果包含非常复杂、大量的元素标签和 DOM 节点，性能开销会随节点数量的增加而增大。因此，SVG 适用于图标等一些简单的元素。
   (b) Canvas：适合于粒子物理效果渲染、游戏等场景。

## 口述点评

**评分：8/10**

**总体评价**：三个维度切得准且排序合理——位图/矢量定本质，JS 绘图/DOM 操作讲机制，性能拐点落到选型，是一份可以直接拿去面试的答案。三处都讲到了「所以」，不是罗列差异，这点很好。

- **Canvas 缺了「没有元素级事件」的另一半**：你说了 SVG 的 DOM 能绑事件，但没点出对应的反差——Canvas 上点击某个图形浏览器**根本不提供命中检测**，得自己算几何或做离屏颜色缓冲。这是「JS 绘图 vs DOM 操作」这条差异最实战的后半句，补上才算完整。
- **漏了可访问性与 SEO 整个维度**：Canvas 画出来的文字不可选中、不可搜索、读屏软件完全读不到；SVG 的文本是真实文本，可被索引和朗读。做数据可视化选型时这是硬性考量，面试官很爱从这里切入。
- **「位图缩放会模糊」只讲了现象，没给工程解法**：真正的坑在 `<canvas>` 的 `width`/`height` **属性**决定像素缓冲区大小、CSS 决定显示尺寸，两者搞混（或高分屏不按 `devicePixelRatio` 放大缓冲区）才会糊。说出这一层，比「位图会糊」高一个档次。
- **机制层可以再点一句术语**：Canvas 是**立即模式**（改一个图形要清空整块重绘、没有图形对象），SVG 是**保留模式**（图形是浏览器维护的 DOM，增量重渲染）。这两个词一出来，前面的差异就都成了推论。另外「SVG 适用于图标等简单元素」略窄——节点数可控但交互丰富的图表（如流程图、组织图）也是 SVG 的主场。
