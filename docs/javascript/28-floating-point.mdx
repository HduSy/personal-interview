# 28. 0.1 + 0.2 === 0.3 表达式返回什么？

## 高频问答

### 1. 面试官：0.1 + 0.2 === 0.3 表达式返回什么？

**回答**：**false**。JS 里 `0.1 + 0.2` 的实际结果是 `0.30000000000000004`，不是 0.3——但 `0.1 + 0.2 === 0.30000000000000004` 是 true。

根因一句话：JS 的 Number 是 **IEEE 754 双精度二进制浮点数**，0.1 和 0.2 在二进制里是无限循环小数，存储时必须舍入截断，两个带误差的近似值相加，结果再做一次舍入，恰好落在离 0.3 最近的那个可表示数的右边一位。这不是 JS 的 bug，所有用 64 位二进制浮点的语言（Java 的 double、Python 的 float）结果一样。

### 2. 面试官：为什么二进制存不下 0.1？0.5 不是好好的吗？

**回答**：二进制小数每一位的权重是 1/2、1/4、1/8……所以**只有分母是 2 的幂的分数能精确表示**：0.5（1/2）、0.25（1/4）、0.75（1/2 + 1/4）都没问题。0.1 = 1/10，分母 10 含质因数 5，用 2 的幂凑不出来，二进制展开是无限循环——与十进制写不尽 1/3 是同一个道理。

双精度浮点数的**尾数只有 52 位**（加上隐含的首位 1，共 53 位有效），无限展开只能舍入截断：存进内存的 0.1 实际是 0.1000000000000000055511151231257827…（`(0.1).toFixed(20)` 可以看到），0.2 同理带误差。两个「略微偏大」的数相加，和再舍入一次，结果就跳到了 0.3 的下一个可表示数。

### 4. 面试官：那浮点数怎么比较相等？金额计算怎么办？

**回答**：三个层次的方案：

- **容差比较**：`Math.abs(a - b) < Number.EPSILON`——适用于数值在 1 附近量级的比较；数字一大就不能这样比（边界在加深理解里）；
- **整数化**：金额以「分」为单位**全程整数运算**（199 分而不是 1.99 元），只在展示层除回去。**不能靠「浮点算完乘 10 再除回去」**——这条对 0.1 + 0.2 恰好成立，对 0.14 × 100 就翻车（得 14.000000000000002），成立与否取决于每一步舍入的运气；
- **任意精度**：小数用 decimal.js / big.js 这类十进制库；BigInt 只支持整数。纯求和场景 ES2026 的 `Math.sumPrecise` 能消除累加误差（[ES 新特性题](/javascript/07-es-new-features)）——但它只修「累加」的误差，单个 0.1 的存储误差依然存在。

### 5. 面试官：toFixed 能解决吗？

**回答**：不能当计算工具。toFixed 有两个问题：**按 double 的实际存储值舍入**——1.005 的存储值比 1.005 略小，`1.005.toFixed(2)` 得 `"1.00"` 而不是 `"1.01"`；**返回字符串**，不转数字没法继续算。展示层的格式化用它没问题，参与运算与相等判断不可靠。

### 6. 面试官：整数为什么没这个问题？2 的 53 次方减 1 是怎么来的？

**回答**：53 位有效尾数（52 显式 + 1 隐含）能精确表示**绝对值不超过 2^53 − 1 的所有整数**——这就是 `Number.MAX_SAFE_INTEGER` = 9007199254740991 的来历。超过这个界，相邻两个可表示数的间隔变成 2，`2 ** 53 + 1 === 2 ** 53` 是 true，加的 1 直接被舍入吞掉。

判断用 `Number.isSafeInteger()`；超界整数用 BigInt。实际项目里最常见的坑：后端返回 64 位的雪花 ID，超过 2^53，`JSON.parse` 后精度已丢——解法是后端把长整型序列化成字符串传输，或前端用支持大整数的解析库。

### 7. 面试官：能总结一下吗？

**回答**：用一张速查表收尾：

| 需求 | 做法 | 注意 |
| --- | --- | --- |
| 判断浮点相等 | `Math.abs(a - b) < Number.EPSILON` | 只在 1 附近量级有效，大数要放宽容差 |
| 金额计算 | 以分为单位全程整数运算 | 不能浮点算完再乘除回去（0.14 × 100 翻车） |
| 任意精度小数 | decimal.js / big.js | BigInt 只支持整数 |
| 多个数求和 | `Math.sumPrecise`（ES2026） | 只修累加误差，不修存储误差 |
| 展示层格式化 | toFixed / toPrecision | 返回字符串；1.005.toFixed(2) 是 "1.00" |
| 大整数（雪花 ID 等） | 后端传字符串 / BigInt | 超过 2^53 − 1 后精度丢失 |

## 加深理解

### 为什么打印出来恰好是 0.30000000000000004，不多不少

`0.30000000000000004` 的实际存储值是 0.30000000000000004440892098500626…，打印并没有把全貌显示出来。JS 把 Number 转成字符串的规则是**最短往返表示**：在所有能舍入回同一个 double 的十进制数里，选最短的那个。所以 `0.1 + 0.2` 显示 17 位有效数字就停了，而 0.1 自己显示成 `"0.1"`——因为 0.1 这个短字符串舍入回去恰好就是那个 double。看到的永远是「够定位的最短版本」，不是存储真身。

### EPSILON 容差为什么只在小数量级有效

Number.EPSILON = 2^-52，它是 **1 与下一个可表示数的间隔**，不是「任意两个数的安全误差」。double 的可表示数间隔随数值大小增长：在 1e16 附近，间隔已经是 2——`1e16 + 0.1` 和 `1e16 + 0.3` 会被舍入成**同一个 double**（都等于 1e16），用 EPSILON 比较自然返回「相等」。大数场景的容差要跟着量级走：`Math.abs(a - b) <= Number.EPSILON * Math.max(Math.abs(a), Math.abs(b))`。

### 「乘 10 除回去」的偏方为什么时灵时不灵

每一步浮点运算都可能舍入：0.1 × 10 的真实乘积离 1 更近，舍入后恰好回到 1；0.14 × 100 的真实乘积离 14.000000000000002 更近，就回不到 14。偏方成立与否取决于中间值的舍入落点，**没有规律可保证**——所以「先乘成整数」必须是「从输入起就是整数」（后端发分、解析时不经过小数），而不是「浮点算到一半再乘」。
