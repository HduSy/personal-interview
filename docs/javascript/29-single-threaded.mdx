# 29. 如何理解 JS 单线程？

## 高频问答

### 1. 面试官：如何理解 JS 单线程？

**回答**：**JS 同一时刻只执行一段代码，只有一个调用栈**——前一段没执行完，后一段进不来。三层理解：

- **执行模型**：所有代码在唯一的调用栈上排队执行，函数调用进栈、执行完出栈；
- **为什么这样设计**：JS 的本职是操作 DOM、响应用户交互。如果多线程，两个线程同时改同一个 DOM（一个删节点、一个改这个节点的内容），就必须引入锁来处理竞态，浏览器脚本环境的复杂度不可控。单线程直接消灭了锁、死锁、竞态，DOM 操作天然安全；
- **配套机制**：单线程不是「什么都排队干等」——耗时 IO 交给异步（事件循环调度），耗时计算交给 Web Worker 后台线程。被设计成单线程的只是「JS 代码的执行」这一件事。

### 2. 面试官：单线程和异步不矛盾吗？异步是谁在等？

**回答**：不矛盾。关键是「JS 单线程」说的是 **JS 的执行**，不是整个浏览器。浏览器本身多线程：JS 引擎线程之外还有定时器触发线程、网络请求线程、GUI 渲染线程等。异步任务的**等待阶段由宿主的这些线程完成，不占 JS 线程**；等待结束后回调被放进任务队列，JS 主线程跑完手头的同步代码，才从队列取下一个执行（[事件循环题](/javascript/19-event-loop)）。所以单线程照样能同时发 10 个请求——等的是网络线程，JS 只负责发起和接回调。

### 3. 面试官：为什么一段长任务会把页面卡死？

**回答**：**GUI 渲染线程与 JS 引擎线程互斥**——JS 执行期间渲染暂停。浏览器每帧约 16.7ms（60fps），要在其中排下 JS 执行、样式计算和绘制；一段同步任务跑 200ms，这 200ms 里点击不响应、动画不动、画面不刷新，用户感知就是「卡死」。交互演示：

<Sandpack
  template="static"
  height={230}
  html={`<div style="font-family: system-ui; padding: 12px;">
  <button id="ping" style="padding: 6px 14px;">点我</button>
  <button id="block" style="padding: 6px 14px;">阻塞主线程 2 秒</button>
  <div style="margin-top: 8px; font-size: 13px; color: #666;">
    先点「点我」看正常响应；再点阻塞按钮，阻塞期间狂点「点我」观察
  </div>
  <div id="log" style="margin-top: 10px; font-size: 13px; color: #334; line-height: 1.8;"></div>
</div>`}
  js={`const logEl = document.querySelector('#log');
const stamp = () => new Date().toLocaleTimeString('en-GB', { hour12: false });
const log = (msg) => {
  const div = document.createElement('div');
  div.textContent = stamp() + '  ' + msg;
  logEl.prepend(div);
};

document.querySelector('#ping').onclick = () => log('click 响应了');
document.querySelector('#block').onclick = () => {
  log('开始阻塞 2 秒 —— 这期间狂点「点我」试试');
  const start = Date.now();
  while (Date.now() - start < 2000) {}   // 同步空转：唯一的调用栈被占死
  log('阻塞结束 —— 刚才点的点击此刻才被处理');
};`}
/>

阻塞期间点「点我」没有反应，但**点击没有丢**——事件被排队，阻塞结束才依次处理。这就是单调用栈的直接后果：回调只能等当前代码让出主线程。

### 4. 面试官：耗时任务怎么不阻塞页面？

**回答**：三个方向——**挪、拆、让**：

- **挪**：纯计算任务挪进 Web Worker 后台线程，算完 postMessage 把结果传回来，主线程全程空闲（Worker 不能碰 DOM，UI 单线程的边界不变，[Web Worker 题](/javascript/01-web-worker)）；
- **拆**：不能挪的（要操作 DOM 的）拆成小批，每批之间用 setTimeout 让出主线程，给渲染和点击留出处理窗口；
- **让**：不紧急的任务（打点上报、预加载）用 requestIdleCallback 排到浏览器空闲时执行（[定时器调度题](/javascript/25-settimeout-vs-raf-vs-ric)）。

### 5. 面试官：单线程带来什么好处和代价？

**回答**：**好处**：无需锁、没有竞态，代码执行顺序可预测，DOM 操作天然安全，编程模型简单。**代价**：一段代码失控（死循环、超长计算），整个页面跟着失去响应；CPU 密集任务没有原生并行——Worker 是补救，但数据通信要走结构化克隆，有拷贝开销。

### 6. 面试官：能总结一下吗？

**回答**：用一张速查表分清「谁在单线程、谁不在」：

| 环节 | 是否单线程 | 说明 |
| --- | --- | --- |
| JS 代码执行 | ✅ 单线程 | 唯一调用栈，一次只执行一段 |
| DOM / 页面渲染 | 与 JS 互斥 | JS 执行期间渲染暂停 |
| 定时器计时 | ❌ 宿主线程 | 到点把回调放进队列 |
| 网络请求等待 | ❌ 宿主线程 / 网络进程 | 等待不占 JS 线程 |
| Web Worker | ❌ 独立线程 | 真并行，但不能碰 DOM |

## 加深理解

### 「Node 也是单线程」这个说法准确吗

准确的部分：JS 代码执行和事件循环在主线程上，是单线程。不完整的部分：Node 的 libuv 提供**线程池**（默认 4 条），文件读写、DNS 解析、加密这类阻塞操作被丢进线程池执行，完成后回调进队列；网络 IO 主要靠操作系统的事件驱动非阻塞接口，不占线程。所以「Node 单线程」与浏览器一样，指的都是「JS 的执行单线程」，宿主环境始终有别的线程在干活。

### 为什么渲染和 JS 必须互斥

渲染过程要读 DOM、样式和布局，JS 随时可能修改它们；如果渲染到一半 DOM 被改，这一帧画面的前后部分就不一致。互斥是成本最低的一致性保证：要么先把 JS 执行完再渲染，要么渲染期间不跑 JS。每次「点击不响应」，付出的都是同一个代价——一致性换来了互相等待。

### 并发和并行在这题里怎么区分

单线程**不能并行**（同一时刻执行多段代码），但**能并发**（交替推进多个任务）：异步回调让单线程在等待间隙处理别的事，这是单线程撑起高并发的机制。Web Worker 提供的是真并行，代价是不能碰 DOM。一句话：并发是任务级的交替处理，并行是执行级的同时进行。
