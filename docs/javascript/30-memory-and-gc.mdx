# 30. JS 如何进行内存管理和垃圾回收？

## 高频问答

### 1. 面试官：JS 如何进行内存管理和垃圾回收？

**回答**：JS 的内存管理是**自动的**：开发者只管**分配**（对象字面量、new、闭包），**回收**由引擎的**垃圾回收器（GC）**完成——JS 没有手动释放，能做的只有解除引用，让对象变成「垃圾」。

GC 判定垃圾的标准是**可达性**：从**根**（全局对象、当前调用栈上的变量和参数）出发，沿引用能走到的对象是活的；**从根走不到的对象就是垃圾**。主流算法是**标记-清除**：从根出发把所有可达对象标记一遍，没被标记的直接回收。V8 在此基础上做**分代回收**：对象按寿命分到新生代和老生代，用不同策略分别回收，降低停顿（第三问展开）。

### 2. 面试官：早期为什么用过引用计数？它为什么被淘汰？

**回答**：**引用计数**的思路是给每个对象记「被引用的次数」，归零就回收。优点是即时——计数一归零马上能收；**致命缺陷是循环引用收不掉**：A 引用 B、B 引用 A，两者计数永远是 1，哪怕外面已经没有任何路径到达它们，照样占着内存不还（老版本 IE 的 DOM 对象用引用计数，加上 JS 闭包形成环，泄漏就是这么来的）。

**标记-清除不数引用，看可达性**：从根遍历标记，A、B 互相引用但从根不可达，两个都标不上，一起回收。所以现代引擎（V8、SpiderMonkey、JavaScriptCore）全部采用标记-清除及其变体，**循环引用在现代 JS 里不构成泄漏**。沙箱现场验证：

### 3. 面试官：V8 的分代回收是怎么回事？

**回答**：依据「多数对象朝生夕死」的规律，V8 把堆分成两代、各用最合适的算法：

- **新生代**（小，几 MB 量级）：存短命对象，用**半空间复制（Scavenger）**——内存分 From、To 两半，GC 时把 From 里存活的对象复制到 To，From 整体一次丢弃、两半互换。复制成本只跟**存活对象数量**相关，短命对象多时几乎没东西要复制，极快；存活过两轮（或 To 空间占用超限）的对象**晋升**老生代；
- **老生代**（大）：存长寿对象，用**标记-清除**回收不可达对象，碎片化严重时再跑**标记-整理**（把存活对象挪到一起，消灭碎片）；
- **停顿优化**：老生代的标记被拆成增量、并发执行（主线程继续跑 JS，标记在后台线程推进），把全停顿从几十毫秒压到毫秒级——动画不掉帧靠的就是它。

### 4. 面试官：既然自动回收，为什么还会有内存泄漏？

**回答**：GC 只回收「不可达」的对象，**泄漏的本质是「不该活着的对象一直可达」**——引用被无意保留了。五类高频场景：

- **意外的全局变量**：函数里 `leaked = 'x'` 没声明，挂到全局活到页面关闭；
- **遗忘的定时器**：setInterval 的回调持着组件实例或大对象，不清 clearInterval，整条引用链都活着；
- **未解绑的事件监听**：监听器挂在 window / document 这类长寿命对象上，回调闭包攥着组件数据，反复绑定还不移除；
- **游离的 DOM 引用**：节点已从文档移除，但 JS 变量或缓存还指着它——它连同整棵子树都回收不了；
- **无上限的缓存**：Map 只进不出，越攒越大。

### 5. 面试官：内存泄漏怎么排查？

**回答**：Chrome DevTools 三板斧：

1. **Performance 面板**看趋势：JS Heap 曲线正常的 GC 是锯齿状回落；**只涨不跌、阶梯式上升**就是泄漏信号；
2. **Memory 面板打堆快照**：操作前后各拍一份，对比 Diff，重点看新增的 `Detached` 开头的节点（游离 DOM）和 Retained Size 大的对象，Retainers 面板直接回答「谁在拽着它」；
3. **Allocation instrumentation**：记录每笔分配的时间线，定位到具体哪段代码在反复造对象。

调试期的干扰项：DevTools 打开时 `console.log` 的对象会被控制台持有，快照里看着像泄漏——排查时先清空 console。

### 6. 面试官：WeakMap 和垃圾回收有什么关系？

**回答**：普通引用（变量、Map 的键）会**阻止**对象回收；**WeakMap / WeakSet 持的是弱引用，不阻止回收**——键对象除了 WeakMap 没别人引用时，GC 会连键带值一起收走。两个用途：给对象挂**元数据**（DOM 节点 → 状态，节点销毁数据自动跟着走，不用手动清理）；做**对象维度的缓存表**而不延长对象寿命。代价是没有 size、不能遍历——成员随时可能被回收，暴露全量没有意义（[Map 和 Object 题](/javascript/24-map-vs-object)、[Set 和 Array 题](/javascript/23-set-vs-array)讲过）。同族工具：`WeakRef` 持弱引用还能事后读取；`FinalizationRegistry` 在对象被回收时发通知（第二问沙箱就是用它看到 GC 的）。

### 7. 面试官：能总结一下吗？

**回答**：泄漏场景速查表收尾：

| 泄漏源 | 成因 | 修复 |
| --- | --- | --- |
| 意外全局变量 | 未声明赋值挂到全局 | 严格模式（直接报错）/ lint 检查 |
| 遗忘的定时器 | 回调引用链持有对象 | clearInterval / clearTimeout |
| 未解绑事件监听 | 挂在长寿命对象上 | removeEventListener / AbortController 统一解绑 |
| 游离 DOM | 节点移除了引用还在 | 不缓存节点 / 用 WeakMap / 置 null |
| 无上限缓存 | Map 只进不出 | WeakMap（键可回收）/ LRU 上限 |

## 加深理解

### 为什么新生代用复制、老生代用标记整理

两代的对象存活率相反：新生代死得多活得少，「把活的搬走、整块丢弃」最划算，成本正比于存活对象数；老生代存活率高，全部复制一遍太贵，只回收不搬（标记-清除），碎片化累积到影响分配时才做一次整理（标记-整理）。算法跟着「存活率」选，这是分代设计的出发点。

### 为什么不能手动触发垃圾回收

GC 的调度（什么时候收、收哪代、停多久）由引擎根据内存压力和分配速率自主决定，目标是把停顿摊到用户无感。JS 不提供触发接口——`window.gc()` 只在 Chrome 加特定启动参数时存在，仅供测试。开发者能影响的只有「让对象尽快不可达」，触发时机永远不归你管。

### 内存抖动：不是泄漏，也一样伤性能

热路径上反复创建临时对象（循环里拼字符串、每帧 new 数组、频繁建闭包），即使都被及时回收，也会推高 GC 频率——每次回收都是一次停顿，体现在页面上就是掉帧。这叫**内存抖动**（allocation churn），与泄漏的区别：泄漏是内存降不下来，抖动是内存锯齿过密。解法是复用对象、池化、减少中间结构。
