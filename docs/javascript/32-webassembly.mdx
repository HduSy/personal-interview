# 32. 如何理解 WebAssembly？

## 高频问答

### 1. 面试官：如何理解 WebAssembly？

**回答**：WebAssembly（缩写 wasm）是一种**可移植的二进制指令格式**，定位是**编译目标**：C、C++、Rust、Go 这类语言编译成 `.wasm` 二进制模块，由浏览器里的虚拟机执行，速度接近原生程序。三个关键词拆开理解：

- **二进制**：不是文本，体积比等价 JS 小、解析更快；
- **静态类型**：变量类型（i32、i64、f32、f64）编译期就确定，和 JS 运行时才确定类型的模型相反；
- **沙箱执行**：跑在和 JS 同一套同源安全模型里，不能越出沙箱访问宿主资源。

它不取代 JS——HTML、CSS、JS 之外，浏览器第一次原生支持了另一种语言的运行格式，两者是配合关系（第三问展开）。

### 2. 面试官：有 JS 了，为什么还需要它？快在哪？

**回答**：短板在计算密集任务上。JS 是动态类型，引擎只能靠 JIT 边跑边优化：先解释执行、猜测类型、优化成机器码，猜错了再**去优化**回退重来——预热和回退让性能不可预测。图像编解码、物理模拟、加密这类纯计算热点，在这套模型下不划算。

WASM 的类型在编译期就定死了，浏览器拿到 `.wasm` 不需要猜测：直接编译成机器码，没有预热、没有去优化、没有 GC 停顿（内存手动管理）。所以 wasm 的优势不只是峰值速度，更重要的是**性能可预测**——这对游戏、音视频这类场景是决定性的。

两个边界要说清：一是「接近原生」指计算，DOM 密集的任务搬进 wasm 不见得快（第三问）；二是**快不等于不阻塞**——跑在主线程的长计算，不管 wasm 还是 JS，照样占死调用栈卡住渲染，该进 Worker 还是要进（[Web Worker 题](/javascript/01-web-worker)、[单线程题](/javascript/29-single-threaded)）。

### 3. 面试官：WebAssembly 能取代 JS 吗？

**回答**：不能。两个硬边界：

- **不能直接操作 DOM**：wasm 模块里没有 DOM 概念，改页面必须回到 JS；
- **Web API 大多也要经由 JS**：wasm 通过「导入」声明它需要的外部函数，由宿主（JS）把这些函数传进来——文件、网络、定时器都是这么接上的。

所以真实架构是**分工**而不是替换：JS 写 UI 和胶水代码（业界通称 glue code），wasm 承载计算内核。互相调用是双向的：JS 调 wasm 的**导出**函数，wasm 调 JS 的**导入**函数。还有一条隐性成本：跨界调用本身有开销，参数要在两套类型系统之间转换——一个循环里每帧都跨界调 wasm 的代码，可能比纯 JS 更慢。适合 wasm 的是「一次跨界、内部长时间计算」的形状。

### 4. 面试官：JS 怎么调用 WASM？写代码看看。

**回答**：拿到 `.wasm` 二进制后用 `WebAssembly.instantiate` 实例化，导出的函数直接当 JS 函数调。真实项目里用 fetch + `instantiateStreaming` 加载编译产物（要求响应头 `Content-Type: application/wasm`）。这里为了演示，把一个 41 字节、导出 `add(i32, i32) → i32` 的模块直接以字节形式内联：

<Sandpack
  template="static"
  showConsole
  height={200}
  html={`<p style="font-family: system-ui; padding: 12px; color: #666; font-size: 13px;">
  打开下方 Console 查看调用结果
</p>`}
  js={`// add(i32, i32) -> i32 的 wasm 模块，字节形式内联
const bytes = new Uint8Array([
  0,97,115,109,1,0,0,0,        // 魔数 "\\0asm" + 版本 1
  1,7,1,96,2,127,127,1,127,    // 类型段：入参 i32 × 2，返回 i32
  3,2,1,0,                     // 函数段
  7,7,1,3,97,100,100,0,0,      // 导出段：导出函数 "add"
  10,9,1,7,0,32,0,32,1,106,11, // 代码段：local.get 0 + local.get 1 + i32.add
]);

WebAssembly.instantiate(bytes).then(({ instance }) => {
  const { add } = instance.exports;      // 导出函数，直接当 JS 函数调用
  console.log('add(1, 2) =', add(1, 2));
  console.log('add(1.9, 2.9) =', add(1.9, 2.9));           // 参数按 i32 截断成 1、2
  console.log('add(2147483647, 1) =', add(2147483647, 1)); // i32 溢出回绕成负数
});`}
/>

三行输出对应三条类型语义：`add(1.9, 2.9)` 得 **3**——JS 数字传入 i32 参数时被截断（1.9 → 1、2.9 → 2）；`2147483647 + 1` 得 **−2147483648**——i32 溢出是回绕，不是 JS 的精度丢失（[浮点题](/javascript/28-floating-point)讲的 double 语义在这里完全不适用）。数字从「统一的 double」变成「确定的 32/64 位整数与浮点」，是两套运行时最本质的差别之一。

### 5. 面试官：JS 和 WASM 之间怎么传数据？线性内存是什么？

**回答**：wasm 模块的内存是**线性内存**——一块连续的 ArrayBuffer（`WebAssembly.Memory` 对象），JS 和 wasm 同时持有引用、都能读写。传数据的固定形状：**把数据写进这块内存，把偏移量传给 wasm**——wasm 只认偏移量，不认 JS 对象。

推论是：JS 对象、字符串不能直接引用，跨界必须做序列化/反序列化，这是 wasm 开发的主要成本之一。工具链（Emscripten、Rust 的 wasm-bindgen）自动生成这部分胶水代码，日常使用感知不到。和 Web Worker 的 structured clone 不同（[Web Worker 题](/javascript/01-web-worker)），线性内存是**同一块内存的共享视图**，不拷贝——大数据场景下这反而是 wasm 的优势。

### 6. 面试官：实际项目里什么时候会用到？谁在用？

**回答**：典型案例：Figma 的渲染引擎（C++ 编译成 wasm，网页版交互性能对齐桌面版）、Photoshop 网页版、Squoosh 的图像压缩、视频编解码和加密库。共同形状：**CPU 密集的纯计算 + 少量 DOM 交互**。

判断自己的项目要不要上，三个条件同时满足才划算：

- **有 profile 证实的计算热点**——不是「感觉 JS 慢」，是火焰图上真的有一段纯计算吃 CPU；
- **热点与 DOM 交互少**——跨界开销可控（第三问的形状）；
- **团队有对应语言的工具链能力**——Rust/C++ 的构建、调试、体积优化都是真实成本。

三个条件缺任何一个，引入 wasm 换来的只有构建复杂度和包体积，性能不会有变化。多数业务项目用不上 wasm，能说清边界比「用过」更重要。

### 7. 面试官：能总结一下吗？

**回答**：一张表对照两种运行时：

| 维度 | WebAssembly | JavaScript |
| --- | --- | --- |
| 定位 | 其他语言的编译目标 | 浏览器的原生脚本语言 |
| 类型 | 静态（i32 / f64…），编译期确定 | 动态，运行时确定 |
| 数字语义 | 32/64 位整数与浮点，溢出回绕 | 统一 double（[浮点题](/javascript/28-floating-point)） |
| 格式 | 二进制，解析快、体积小 | 文本 |
| 执行 | 直接编译机器码，无预热、无去优化 | JIT 预热 + 可能去优化 |
| 内存 | 线性内存，手动管理 | 引擎托管 + GC |
| DOM | 不能直接操作，经 JS 胶水代码 | 直接操作 |
| 适用 | CPU 密集、少 DOM 的计算内核 | UI、业务逻辑、胶水 |

一句话收尾：**wasm 不是更快的 JS，是浏览器里第二套类型系统和运行时**——快只是它静态类型的副产品。

## 加深理解

### wasm 的沙箱为什么是安全的

模块能访问的东西只有两类：**显式导入**的函数，和**自己的线性内存**。线性内存的每一次读写都带边界检查，越界访问直接 trap（终止执行并抛错），读不到宿主进程的任何内存；想用文件、网络、定时器，必须在导入清单里声明、由宿主给。能力最小化的设计和 JS 沙箱同级，同源策略照常生效——所以加载第三方 .wasm 的风险模型和加载第三方 JS 脚本相当。

### asm.js 是 wasm 的前身

wasm 之前 Mozilla 做过 asm.js：把 C++ 编译成**严格限定类型的 JS 子集**，引擎看到这种代码就跳过类型猜测直接生成机器码。思路成立，但受制于两点——文本格式解析慢，且语法必须兼容 JS。wasm 保留了「静态类型编译目标」的思路，格式从头设计成二进制。今天没有人新写 asm.js，但浏览器里它的痕迹还在：优化 asm.js 风格代码的经验直接进了 JIT。

### WASI：浏览器之外跑 wasm

浏览器之外要跑 wasm，缺的是系统接口——文件、时钟、环境变量。WASI（WebAssembly System Interface）定义了这套标准化系统调用接口，让同一个 .wasm 不改就能跑在服务端、CLI、插件系统里。这把 wasm 从「浏览器技术」扩展成了跨平台沙箱二进制格式，服务端场景（如 Fastly 的边缘计算）已经在用。

### WasmGC：GC 语言的直接编译通道

Java、Kotlin、Dart 这类 GC 语言，以前编译到 wasm 必须把自己的 GC 运行时整个打进模块——体积动辄几 MB。GC 扩展（WasmGC）让这些语言直接使用宿主引擎的 GC，模块体积降到 KB 量级。支持状态：Chrome 119（2023-10）首发，Firefox 120（2023-11）跟进，Safari 18.2（2024-12）补齐——三大引擎现已全部支持。
